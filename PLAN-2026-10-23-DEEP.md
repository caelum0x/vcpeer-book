# VCPeer Book — Deep Build Plan (2026-10-23)

Internal build doc. This repo ships zero app source — every page/API below
is upstream Cal.com (`calcom/cal.com:v6.2.0-arm`, unmodified image), reached
only via config (env vars, `docker-compose.yml`, direct SQL in
`deploy/apply-vcpeer-branding.sql`). "Remaining" items are the only places
new engineering in this repo's actual scope is possible without forking
upstream. UI elements for upstream pages are described as they exist
today (Cal.com's own copy/icons, not ours to relabel without a fork); the
no-emoji/symbol-only-controls rule applies to anything this repo builds
net-new (signup/OAuth-config additions), not to upstream's existing UI.

## 2. APIs (live today, status: DONE, upstream endpoints this repo calls into via the cron sidecar)

| Method + path | Caller | Auth | Cadence | Purpose |
|---|---|---|---|---|
| `POST /api/cron/bookingReminder` | `calcom-cron` sidecar | `authorization: $CRON_API_KEY` header | `*/15 * * * *` | 48h/24h/3h organizer reminder for unconfirmed bookings |
| `POST /api/cron/workflows/scheduleEmailReminders` | `calcom-cron` | same | `*/15 * * * *` | workflow-engine email reminder dispatch |
| `POST /api/cron/changeTimeZone` | `calcom-cron` | same | hourly | timezone migration processing |
| `POST /api/cron/webhookTriggers` | `calcom-cron` | same | every minute | webhook delivery retry queue |

No API route is defined in this repo; all four handlers live in the
upstream image. 401 from any of the above = `CRON_API_KEY` mismatch
between `.env`/`/etc/products/vcpeer-book.env` and the running `calcom`
container — redeploy `calcom-cron` after fixing.

### 3.3 Remaining — ranked, with exact scope

1. **Google/Office365 calendar OAuth connect (real conflict-checking).**
   - What it does: lets Cal.com check the admin's real external calendar
     before showing a slot as free.
   - Data touched: `Credential` (new `google_calendar`/`office365_calendar`
     row for `userId=1`), `Schedule` (admin's working hours, currently 0
     rows — falls back to Cal.com's hardcoded default).
   - Dependencies: a Google Cloud project + OAuth client (Calendar API
     enabled, redirect URI
     `https://book.vcpeer.com/api/integrations/googlecalendar/callback`) —
     **owner blocker**, console + 2FA. Once the client exists, this repo's
     part is two env vars in `/etc/products/vcpeer-book.env`
     (`GOOGLE_API_CREDENTIALS` / client id+secret per cal.diy's
     `.env.example`) plus restarting `calcom`.
   - Remaining after owner step: enable `google-calendar` in
     `/settings/admin/apps`, connect it as the admin at
     `/settings/my-account/calendars` (interactive OAuth consent —
     **owner blocker**, cannot be scripted).

2. **DKIM confirmation for `bookings@vcpeer.com`.**
   - What it does: confirms outbound mail from OCI Email Delivery is
     signed, so confirmation/reminder emails don't land in spam.
   - Data touched: none (read-only check).
   - Dependencies: OCI Email Delivery console access for the
     `vcpeer.com` approved sender — **owner blocker**, no API surface
     reachable from `box` SSH (SPF was checkable via `dig`; DKIM selector
     name is not guessable from outside the console).

3. **Self-serve signup + free/paid tier split** (largest remaining item,
   not started — spec only, do not half-build):
   - What it does: opens a second org/user path without touching the
     existing single-admin internal account.
   - Pages needed (net new, this repo's actual UI-copy rules apply): a
     `/signup` entry point (Cal.com's own flow, re-enabled via
     `NEXT_PUBLIC_DISABLE_SIGNUP=false` for a *separate* org path — not a
     blanket flip, keep the current admin org exactly as-is), a plan-gate
     screen before the public link goes live (free: unlimited event
     types + Jitsi video, no card; paid: custom domain + "Disable Cal.com
     branding" unlocked).
   - API needed: none in this repo if gating is enforced purely via
     Cal.com's own org/teams model; a thin proxy check in front of
     `calcom` only if Cal.com's org model can't express "free until X,
     then require a plan field" — **decide this before writing any code,
     not during**.
   - Data touched: new `Team`/`Membership` rows per signup (upstream
     schema, no migration needed), a new `plan` field if the thin-proxy
     path is chosen (would need its own migration — avoid if the org
     model suffices).
   - Dependencies: none owner-blocked, but is a multi-day build — do not
     start piecemeal; plan the gating mechanism fully first (see
     `STRATEGY-2026-10-23.md` section 5, move 1, for the product
     rationale this plan doesn't repeat).
   - Explicitly not started this pass — too large for a single build
     pass without re-deriving the gating decision first.
