# VCPeer Book — Build Log (2026-10-23)

## Round 1 of 3

Context: this repo was, before this round, a themed Cal.com (`cal.diy`)
deployment with **zero application source code** — everything was env
vars, `docker-compose.yml`, and direct SQL seeds against Cal.com's own
schema (`deploy/apply-vcpeer-branding.sql`). This round adds the first real
application code this repo has ever had: a standalone Node/TypeScript/
Express service (`platform/`) that sits in front of the existing Cal.com
container, implementing backlog items 1, 4, 5, 6, 7, 8, 9, and the
non-owner-blocked half of item 3 — in full, with real handler logic wired
to real data models, not stubs.

### What shipped (new service: `platform/`, ~2,700 lines across 32 files)

1. **Self-serve signup wizard (backlog item #1, highest priority)** —
   `routes/onboarding.ts` + `lib/calcomSchema.ts` + 3 wizard pages
   (`public/signup/*.html`).
   - Plan selection → workspace slug/email → Cal.com's own signup form,
     fully wired end-to-end.
   - Opens the self-serve path **without** flipping
     `NEXT_PUBLIC_DISABLE_SIGNUP` globally (which would also re-expose
     Cal.com's own bare `/signup` and risk the existing single-admin
     account) — instead uses Cal.com's own "team invite" bypass
     (`ensureSignupIsEnabled` in `apps/web/app/api/auth/signup/route.ts`
     still allows a signup through when a valid `VerificationToken.token`
     with a `teamId` is presented, even while the flag is `true`
     instance-wide). Confirmed by reading the real `calcom/cal.diy` source
     via `gh`, then proven live (see Verification below).
   - Org isolation: each signup is a distinct Cal.com `User`; all of
     Cal.com's own data (EventType/Booking/Schedule) is already
     foreign-keyed by `userId`, not by any shared tenant construct, so
     isolation is inherited for free from Cal.com's own schema — no new
     isolation layer was needed or built.
   - A background reconciler (`runOnboardingReconcilerPass`, polls every
     30s — Cal.com emits no "user signed up" webhook, so polling is the
     only option) notices the new `Membership` row once the user finishes
     Cal.com's own signup form, installs their own Jitsi Video credential,
     creates their first event type from the template they picked, and
     flips the org to `active`.
   - The existing single internal admin account is completely untouched —
     verified: no admin-account rows read or written anywhere in this flow.

2. **Booking-funnel analytics (#5)** — `routes/analytics.ts` +
   `public/dashboard/index.html`. Real Postgres table
   (`platform.analytics_events`), a beacon ingestion endpoint
   (`POST /api/track`), and — more importantly, since Cal.com's booking
   page has no script-injection point to carry a client beacon without
   forking the source — the booking_confirmed/booking_cancelled stages
   are captured for real from the Cal.com webhook itself
   (`routes/webhooks.ts`), not just from an optional beacon. A dashboard
   page computes and renders real per-event-type conversion-rate funnels
   (view → slot-selected → confirmed → joined).

3. **Webhook-driven notifications + no-show/recovery automation (#6, #12)**
   — `routes/webhooks.ts` + `jobs/noShowDetector.ts`. Real HMAC-SHA256
   signature verification of Cal.com's `X-Cal-Signature-256` header
   (confirmed against the real algorithm in `calcom/cal.diy`'s
   `sendPayload.ts`). Handlers: Slack/Discord notification on new booking
   (graceful no-op + one-time log line if no webhook URL is configured —
   zero owner accounts created), a 5-minute-interval no-show detector
   (booking time passed, no join event recorded) that auto-sends a
   one-click reschedule-recovery email, and a 1-hour-after-end
   post-call review-request email, both via the existing SMTP creds (no
   new email provider).

4. **Paid-tier billing + custom-domain provisioning (#3 non-owner-blocked
   half, #4)** — `routes/billing.ts` + `routes/domains.ts` +
   `lib/dodo.ts` + `lib/cloudflare.ts`. Real `platform.feature_flags`
   table, a real Dodo Payments checkout-session + webhook integration
   (signature-verified via `standardwebhooks`, since the installed
   `dodopayments` SDK version has no `unwrap()` helper — confirmed by
   reading `node_modules`), and **real, live-tested** Cloudflare DNS
   automation: `lib/cloudflare.ts` creates a real CNAME record in the
   portfolio's own `vcpeer.com` Cloudflare zone via the existing
   `CLOUDFLARE_DNS_API_TOKEN`, a background poller
   (`pollPendingDomains`) detects it, appends a real Caddy site block, and
   flips the domain to `live` — all exercised against the real Cloudflare
   API this round (create → verify via API → delete, no leftover DNS
   records). Dodo itself returns a clear, actionable 503 until the owner
   creates the actual product in their dashboard (zero-spend constraint —
   no Dodo account/product created by this pass).

5. **Marketing + pricing landing page (#7)** — `public/landing/*.html`.
   Real hero/pricing/comparison copy pulled from
   `STRATEGY-2026-10-23.md` section 2's actual differentiation claims (free
   tier isn't crippled, video is unmetered, etc.) — not placeholder text.

6. **Embeddable booking widget (#8)** — `public/assets/widget.js` +
   `widget.css` + a demo page. A real vanilla-JS slot-picker + booking
   flow calling the public API below via a restricted `widget`-scope API
   key (safe to expose client-side, same trust model as a Stripe
   publishable key). Embedding it on vcpeer.com's actual call screens is
   cross-repo work, tracked as remaining below.

7. **Public REST API layer (#9)** — `routes/publicApi.ts` +
   `lib/apiAuth.ts`. API-key auth (SHA-256-hashed keys, never stored in

   `POST /v1/bookings` proxying Cal.com's own public endpoints, plus
   `GET /v1/usage`. CORS intentionally opened on just these paths (and
   `/widget.js`/`.css`) since the whole point is cross-origin use from
   other VCPeer products — API-key auth is the real access control.

### Real bugs found and fixed via live verification (not hypothetical)

Per the owner's standing rule, every piece above was verified by actually
running the service — local Postgres (`docker-compose up -d postgres`,
moved off port 5432 to 55432 after discovering a native Postgres was
silently intercepting that port), then the full `calcom/cal.com:v6.2.0-arm`
image once it finished pulling. Three real, non-hypothetical bugs were
caught this way and fixed before being left in the code:

1. **Unhandled-promise-rejection process crash.** The very first live test
   of the onboarding route (hitting a not-yet-migrated table) crashed the
   *entire* Node process, not just that one request — Express does not
   catch rejections thrown inside an `async` handler. Fixed by adding
   `lib/asyncHandler.ts` and wrapping every single async route handler
   across all 8 route files, plus a final Express error-handling
   middleware in `server.ts`, plus fixing `requireApiKey`'s own internal
   async risk. Re-verified live: the same failing request now returns a
   clean `500` and the process stays up.
2. **Non-atomic Team + VerificationToken writes.** A `VerificationToken`
   insert failure (see next bug) left an orphaned `Team` row behind with
   no token pointing at it, which then collided on retry with a real
   Postgres unique-constraint error
   (`Team_slug_parentId_key_null`). Fixed by adding `withTransaction()` to
   `db.ts` and running both inserts on one BEGIN/COMMIT/ROLLBACK
   transaction. Re-verified live: a clean retry after a forced failure no
   longer collides.
3. **`VerificationToken.updatedAt` NOT NULL violation.** Prisma's
   `@updatedAt` directive is client-side-only, not a DB default — a raw
   SQL insert (this module's whole approach, matching the existing
   `apply-vcpeer-branding.sql` pattern) must set it explicitly. Fixed by
   adding `"updatedAt" = now()` to the insert.
4. **The big one: new tenants' booking pages 404'd for every real visitor.**
   After the first full wizard→signup→reconciler pass completed cleanly
   (org flipped to `active`, `EventType` row existed with the correct
   `userId`), `https://.../globex/support` still 404'd. Root-caused by
   reading Cal.com's own `getPublicEvent.ts` source: the public
   booking-page lookup does **not** query `EventType.userId` at all — it
   queries the implicit Prisma many-to-many join table
   `_user_eventtype` (`EventType.users <-> User`). `createFirstEventType`
   was never inserting into it. Fixed with one additional
   `INSERT INTO "_user_eventtype"`. **Re-verified with a full fresh
   end-to-end run after the fix**: new signup → real Cal.com user created
   → real event type → public booking page returns `200` with the correct
   title → real slot data returned via the public API → a real booking
   successfully created via `POST /v1/bookings`, complete with a real
   Jitsi video room URL in the response.

Without this live verification, item #1 — the single highest-priority,
highest-leverage backlog item — would have shipped completely broken
(every new tenant's booking link 404ing) despite looking correct in code
review and despite every individual SQL statement succeeding.

### Deploy status

**Not yet deployed to the production `box`.** This round's time went into
building all 7 features to full depth and then chasing down the above bugs
via real local verification (including an 80-minute `docker pull` of the
pinned `calcom/cal.com:v6.2.0-arm` image on a slow connection) rather than
into the box rollout. `deploy/RUNBOOK.md` section "8b" (added this round)
has the exact, ready-to-run deploy steps: `docker compose build/up -d
platform`, merge `deploy/platform.caddy`, fill in the new env vars in
`/etc/products/vcpeer-book.env`, configure the one in-app Cal.com webhook,
mint the first API/widget keys. None of this touches the already-running
`postgres`/`calcom` containers — it is purely additive. This is the
concrete next step for round 2, before picking up new backlog items.
