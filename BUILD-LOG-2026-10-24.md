## 3. Real bug found and fixed: custom-domain Caddy provisioning was dead on arrival

While deploying, read `routes/domains.ts`'s `appendCaddyBlock` /
`reloadCaddyIfLocal` closely enough to trace exactly where the rendered
Caddy snippet would land in production, and found it never could have
worked:

1. `CADDY_SNIPPET_PATH` was `path.join(__dirname, "..", "..", "..",
   "deploy", "custom-domains.caddy")`. `__dirname` for the compiled
   `dist/routes/domains.js` inside the container is `/app/dist/routes` —
   three levels up lands at `/`, i.e. the snippet was written to
   `/deploy/custom-domains.caddy` **inside the platform container's own
   ephemeral filesystem**. The host's real Caddy process (running outside
   any container, via systemd) could never see this file, mounted or not
   — nothing mounted it.
2. `reloadCaddyIfLocal()` then did `exec("caddy reload --config
   /etc/caddy/Caddyfile")` — the `platform` container's image (plain
   `node:alpine`-based, see `Dockerfile`) has no `caddy` binary at all, and
   even if it did, it runs in its own PID namespace and couldn't reload the
   host's actual Caddy process without a docker-socket mount (deliberately
   not given one — not worth the privilege escalation for a reload).

Net effect: a custom domain would flip to `status = 'live'` in
`platform.domains` (the Cloudflare DNS record is real, propagation check is
real) while actually 404ing forever on real HTTPS traffic — a shipped
feature that looked done in code review and would have silently failed
for the first real paying customer who tried it.

**Fixed**, verified live end to end:

- `CADDY_SNIPPET_DIR` is now `process.env.CUSTOM_DOMAINS_CADDY_DIR` (falls
  back to the old in-repo path for local dev, where nothing mounts it and
  reload is a no-op anyway via the existing `VCPEER_BOOK_CADDY_RELOAD`
  gate).
- `docker-compose.yml`: added a **bind mount** (not a named volume —
  must be a real host path) `./deploy/custom-domains:/app/custom-domains`
  on the `platform` service, plus `CUSTOM_DOMAINS_CADDY_DIR=/app/custom-domains`.
- `reloadCaddyIfLocal()` no longer shells out to a binary that isn't
  there — it drops a `.reload-requested` sentinel file into the same
  mounted directory.
- New host-side cron, `/etc/cron.d/vcpeer-book-caddy-reload` (root,
  alongside the existing `vcpeer-book-backup` cron): every minute, if the
  sentinel exists, deletes it and runs `systemctl reload caddy`.
- Box's main Caddyfile (both `/opt/infra-box/caddy/Caddyfile` and the
  deployed `/etc/caddy/Caddyfile`, backed up first) now has
  `import /opt/infra-box/stacks/vcpeer-book/deploy/custom-domains/*.caddy`
  right after the existing `sites-enabled` import — additive, confirmed an
  empty-glob import is valid by reloading with the directory still empty
  (just `.gitkeep`) before any real domain exists.
- **Verified live, full loop**: wrote a real `.reload-requested` sentinel
  file through the exact mounted path (confirmed round-trip by writing
  from *inside* the running `platform` container via `docker exec` and
  reading it back on the host); within 60s the cron fired
  (`CRON[...]: (root) CMD (test -f ... && rm -f ... && systemctl reload
  caddy)` in `journalctl`), the sentinel was deleted, and Caddy logged a
  clean `"load complete"` / `"Reloaded caddy.service"` reload — the whole
  mechanism this feature depends on now demonstrably works, where before
  this round it demonstrably could not have.
- Documented as RUNBOOK.md section "8c" (new).
